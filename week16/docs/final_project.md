## Claude Code 로 내 파이프라인 돌리기 (기본 환경 · `../../docs/claude_code_quickstart.md`)
강좌 파이프라인 = 저장소 스크립트(curate → pareto → ehvi_select → md_vs_exp → final_project_check) + Claude Code(실행 · 보고) + 사람 승인. 덱 16 · 17장의 연구 플랫폼(역할 에이전트 · 작업 큐 · 계약 문서)과는 규모 · 구조가 다르고, 원칙은 같다: **선택 = 스크립트 · 정책 · 승인 = 사람 · 언어 모델 = 선택을 바꾸지 않음.**

1. **폴더** · 예시로 시작하려면 Claude Code 에 「`expected_output/example_project` 를 `out/my_project` 로 복사해」 → 승인 창에서 명령 확인 → 승인. 이후 내 값으로 파일을 하나씩 교체.
2. **프로젝트 규칙 = `CLAUDE.md`** · 내 프로젝트를 별도 폴더(또는 저장소)로 옮기면 그 폴더 맨 위에 `CLAUDE.md` 를 두고, 그 폴더에서 `claude` 를 시작하면 자동으로 읽는다(`/init` 으로 초안 · `/memory` 로 수정). 숫자는 내 `problem.json` · `protocol.json` 과 같은 값만 적는다.
   ```markdown
   # 내 최종 프로젝트 규칙
   - 표적 · 방향 · 제약 · 성공 기준 = problem.json (여기와 다르면 problem.json 이 기준)
   - 순서: curate → pareto → ehvi_select → [승인] → MD 재검증 → md_vs_exp → final_project_check
   - 정지 규칙(목표 달성 · 예산 · 무개선) = protocol.json 의 값 · 판정은 표로 보고하고 계속 · 정지는 내가 정한다
   - 승인 지점: 제외 규칙 변경 · MD 재검증 제출 · 정지 판정 · 제출 폴더 파일 수정 · 삭제
   - 강좌 scripts/ 는 고치지 않는다 · 변형은 out/ 아래 새 파일 · 근거 없는 수치 = 「확인 필요」
   ```
3. **대화형 · 한 번 실행** · 명령 실행 · 파일 수정이 있는 단계는 대화형 `claude` 에서 승인하며 진행한다. 읽고 요약만 하는 단계는 `claude -p "지시"`(한 번 실행 후 종료)로 돌린다. 예: `claude -p "out/checklist.json 의 ✗ 항목만 표로"` · W07 배치 큐처럼 같은 점검을 되풀이할 때 편하다. 승인을 모두 건너뛰는 옵션은 쓰지 않는다.
4. **사람 승인 지점** (연구 플랫폼의 승인 게이트 · 덱 16장 ② 에 해당)

   | 지점 | 승인 전에 볼 것 |
   |---|---|
   | 큐레이션 제외 규칙 변경 | 바뀌는 인수 · 남는 행 수 · 이유 기록 |
   | EHVI 추천 → MD 재검증 제출 | 추천 조건 · 예측 ± σ · 적용 영역 · 예상 계산 시간 |
   | 정지 판정(계속 · 정지) | 정지 규칙 3종의 현재 값 · SE 기준 개선 여부 |
   | 제출 폴더 파일 수정 · 삭제 | 바뀌는 파일 · 필드 · 근거 파일 |
5. **기록** · 큰 수정 전 `git commit` · 실패한 시도와 원인은 `limits.md` 「실패한 시도와 원인」 절에 바로 적는다(발표 9장 재료).

## 실측 대조 방식 (덱 22 · 23장 요약)
- **밀도 = 정량**: 측정 온도 · 첨가제로 짝짓기 → 상대오차의 크기와 **부호**를 함께 보고(한쪽 부호 = 계통 오차).
- **Tg = 방향**: 냉각률 차이(MD ~10¹¹ K/s ↔ DSC ~10 K/min)로 절대값은 어긋남 → 노화 · 첨가 방향 비교.
- **강성 = 시간축 정합**: MD G(t) 와 실측 마스터커브의 시계 간격 Δ(이번 예: 4.72 ± 0.39 decade)를 먼저 맞춘 뒤 형상 비교. BBR S · m · MSCR Jnr · G*/sinδ 같은 규격 지표는 MD 가 직접 계산하지 않는다.

## W18 폐루프 결과 사용 (2026-11-14 · 18주 과정 · 위 내용은 그대로 유효)
과정이 18주로 늘었다(W17 MD 워크플로우 조립 · W18 폐루프 통합 실습). 최종 프로젝트는 **W18 폐루프 결과**를 쓴다. W16 의 체크리스트 · 제출 폴더 형식 · 평가 기준은 그대로이고, 제출은 W18 뒤에 한다.

- **쓰는 파일** (`../../loop/` · 이름 = `config/loop.yaml` 의 `name`)
  - `ws/<이름>/db/loop_results.csv` · 후보별 계산 결과(밀도 · CED ± 오차 · 라운드 · 모드)
  - `ws/<이름>/state.json` · 라운드마다 고른 후보 · 가장 가까운 계산 · 정지 판정
  - Obsidian 볼트 노트 · `vault/runs/`(실행 노트) · `vault/rounds/`(라운드 노트 · 「고른 이유」) · `vault/papers/`(근거 문헌 · `[[citekey]]` 링크)
- **「추천 → MD 재검증」**(덱 27장 02) = W18 에서 MD 워크플로우(`../../mdworkflow/`)로 실제 실행한다. W16 의 EHVI 는 이미 계산된 값 안에서 고르고 실제값을 공개하는 방식이었다(덱 11장).
- **제출 폴더와의 대응** (파일 이름 · 평가 항목은 위 표 그대로)
  | 제출 파일 | W18 에서 가져올 것 |
  |---|---|
  | `problem.json` | 문헌 표적(`lit_targets.json` · 밀도 · CED · 판정 폭) · 근거 citekey |
  | `protocol.json` | MD 워크플로우 표준 프로토콜 · `loop.yaml`(모델 · 획득함수 · 배치 · 정지 규칙) |
  | `pareto.json` · `recommendations.csv` | `loop_results.csv` · `state.json` 의 라운드별 후보 · 예측 ± σ |
  | `validation.json` | 문헌 표적과의 거리 · 힘장 점검(`../../mdworkflow/README.md` 「힘장 검증 사례」) |
